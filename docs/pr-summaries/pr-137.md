## Description
## What

Every model call goes to `claude -p` first. When that fails for **any** reason — safeguards refusal, Max-subscription usage limit, timeout, empty output — the same prompt is retried against OpenRouter models in order. Unset `OPENROUTER_API_KEY` = today's behaviour, byte for byte.

| Tier | Primary | Fallback 1 | Fallback 2 |
|---|---|---|---|
| Editorial — window, daily, weekly, positions, patreon (`ANTHROPIC_MODEL`) | `claude-opus-5` | `openai/gpt-5.6-sol` | `z-ai/glm-5.3` |
| Light — translate, context (`TRANSLATE_MODEL`/`CONTEXT_MODEL`) | `sonnet` | `openai/gpt-5.6-terra` | `deepseek/deepseek-v4-flash` |

All legs run at OpenRouter `reasoning.effort: high`. `verify.py` is **excluded** — the only `claude -p` call made *with* tools (WebSearch/WebFetch), which no fallback can honour.

Model ids were taken from OpenRouter's live catalog during planning, not from memory.

## The bug review caught

The draft started the shared budget clock **before** `primary()` ran, charging Claude's own runtime against the fallbacks. At the deployed `CLAUDE_TIMEOUT_SECONDS=600` against a 180s budget, `180 - 600` is negative — so a **timing-out primary skipped every leg without sending one request**. The chain was dead for precisely the failure mode it exists for.

Fixed by starting the clock when the primary fails, and pinned by `test_a_timing_out_primary_still_gets_the_full_fallback_budget`. I verified the test actually catches it: reintroducing the old line makes it fail with the exact `-420.0s left in the 180s shared budget` symptom, and restoring the fix makes it pass.

## Load-bearing design (PLAN.md §4.23)

- **`primary` is a caller-supplied callable, never resolved inside the chain.** ~145 test references monkeypatch `run_claude` as a module *global* across seven modules. A chain calling `run_claude` itself would bypass every one of them — the real CLI subprocess would run inside the suite, green while testing nothing.
- **`validate` runs per leg, inside the loop.** Claude signals refusal structurally (non-zero exit + marker). An OpenRouter model declining returns prose with HTTP 200 — a *successful* call with unusable output. Validating after the chain returned would accept that leg and fail downstream with the next leg never tried. `positions` and `context` pass their own validators so `NO-SIGNAL`/`INSUFFICIENT_CONTEXT` count as success, not as a failed leg.
- **One budget shared across legs**, not one each — a per-leg budget would make the worst case scale with leg count and silently invalidate the systemd ceilings.
- **Empty `fallbacks` re-raises the primary's exception object unchanged** (bare `raise`). `translate_digest` catches `SafeguardsRefusalError` specifically and existing tests assert on the primary's own type.
- **Secrets.** `OpenRouterError` carries only an HTTP status or exception type name — never a body, `str(exc)`, `exc.url`, or the key — mirroring `publish.py`'s `_send_message`, because the request body is our prompt built from scraped Telegram/X text and an error body can echo it back. `FallbackLeg.api_key` is `repr=False`; `OPENROUTER_API_KEY` is deliberately **not** in `claude_subprocess_env()`'s allowlist.

## Cost

`run_openrouter` logs `prompt_tokens`/`completion_tokens`/`reasoning_tokens` per call, so the first real fallback replaces the estimate with a measurement. Modelled on 30 days of actual volumes from the VM's `state.db`: a month with *every* call falling through is ~$34–98 editorial-tier depending on reasoning-token behaviour; realistic fire rates (2–10%) land in single dollars. A per-key spend cap on the OpenRouter side is the real ceiling and is worth setting at creation.

## Model provenance (second commit)

With a chain live, "which model wrote this" is the only way to notice a fallback fired without reading journals. The digest page now carries a second colophon row under the existing sources key:

```
SOURCES   ● news 145  ● x 55  ● telegram 34  ● reddit 13
WRITTEN   ✎ claude-opus-5 · high     ↻ HU openai/gpt-5.6-terra · high
```

`↻` plus muted styling marks a leg a fallback served — the same glyph-not-colour posture `⚠` already uses for a failed source. Renders nothing at all on digests predating the column.

- `run_with_fallbacks` returns `(output, ModelRun)`; `summarize`/`summarize_daily`/`summarize_weekly`/`translate_digest` thread it up. Patreon, positions and context primers discard it — the first two are Telegram-only, and a primer is not a digest.
- **One JSON column** `digests.provenance` (schema v7), not several TEXT ones — matches the `source_counts`/`topics`/`deltas` precedent, one migration, and room for the verify pass to record itself later with no further schema change.
- Site: `migrations/0010-provenance.sql`, `schema.sql`, ingest validation (unknown keys tolerated — forward-compatible with a future `verify` leg), `renderProvenance`, CSS, EN/HU strings.

**`translate_digest` needed a correction the chain cannot make for itself.** Its primary closure is *already* a two-step Claude retry (`TRANSLATE_MODEL`, then `TRANSLATE_MODEL_FALLBACK` on a refusal), and `run_with_fallbacks` can only label the primary path with the one model id it was told about — so a digest translated by the same-provider fallback would have been misreported as translated by the primary. It now tracks which model its inner retry actually used and fixes the `ModelRun` up.

**Golden diff:** all 9 goldens change (`css.js` ships inline on every page); only `digest-235-{en,hu}.html` carry a content diff — the new `<div class="provenance">` row. I corrected the fixture during review: it originally showed `↻ HU sonnet`, but `fallback: true` means an *OpenRouter* leg served, so a Claude model name there is a combination the app can never produce, and the golden doubles as reference documentation.

**Found in passing, not fixed:** SQLite 3.47.1's `ALTER TABLE … DROP COLUMN` fails with a spurious `incomplete input` on the `digests` table, because its re-parse mishandles a `CREATE TABLE` comment whose quoted/braced span is split across two `--` lines. Verified against the real DDL. The pre-existing `kind` column's comment carries the same trap. Zero production impact (nothing ever runs `DROP COLUMN`), but it constrains how migration *tests* can simulate an old database — noted in the new column's own comment so it isn't reintroduced.
