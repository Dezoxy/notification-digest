# PR #74: fix(config): give translation its own timeout instead of the summarizer's

## Description
## The bug this unblocks

`digest-daily.service` on `01-myapps-vm` has failed with `Result=timeout` **every night since at least Aug 14** — delivering the brief successfully, then being SIGINTed seconds later during teardown, firing a spurious `OnFailure` alert each time.

```
Starting 18:31:16 → digest_delivery OK 18:41:11 → systemd kills it 18:41:17
```

## Root cause

`translate_digest` reused `claude_timeout_seconds`. It may call the model **twice** — primary, then `translate_model_fallback` on a safeguards refusal — each at the full timeout it is handed.

At the deployed `CLAUDE_TIMEOUT_SECONDS=600`, the daily run's sanctioned budget is:

| Phase | Budget |
|---|---|
| `summarize_daily` | 600s |
| `verify_daily` | 600s |
| `translate_digest` (primary + fallback) | **1200s** |

**Up to 2400s against a 600s `TimeoutStartSec`.** The unit can be killed while every internal step is behaving exactly as designed and none of them has timed out.

## The change

`TRANSLATE_TIMEOUT_SECONDS` (default **300**) caps both translate legs.

This follows reasoning already in the codebase: `context_timeout_seconds` is a separate knob for exactly this reason, and its comment explicitly names `translate_digest` as the outlier that *"reuses that value outright"*. Translation is a fixed-size rewrite of one already-written body — it never carries the items/coverage payload that sizes `claude_timeout_seconds`, so inheriting a budget scaled for 200 items was incidental rather than intended.

Sizing it separately is what lets the homelab role **assert** a real bound on each run mode's total at deploy time, rather than documenting one and hoping it stays true — which is the drift that caused this bug.

## Tests

Three added, including `test_translate_timeout_is_independent_of_claude_timeout`, which sets the two to different values and fails if anyone re-couples them.
