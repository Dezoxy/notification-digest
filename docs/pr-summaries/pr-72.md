## Why

The homelab timer (`myapps_digest_on_calendar`) is moving from **3-hourly to 6-hourly** (Dezoxy/toom-platform-homelab#707). Two constants in this repo were sized as a **multiple of that interval**, not as absolute hours. Both silently halve their slack unless they move with it.

## `_LOOKBACK_HOURS` — `collectors/rss.py`, 12h → 24h

RSS is the one collector with **no cursor axis**. Telegram/X/Reddit persist a `last_seen_id`, so a longer gap between runs costs them nothing. RSS's idempotency comes purely from `UNIQUE(source, source_id)`, which means the lookback window *alone* decides what is reachable — and anything older is an accepted, permanent miss.

The constant's own comment states the sizing rule outright: **"4x the run interval"**, chosen to tolerate a skipped run or a redeploy window. At 6h, a 12h window leaves 2 runs of slack instead of 4.

24h also happens to match `reddit.py`'s own `_LOOKBACK_HOURS` (24, for the unrelated reason that it mirrors Reddit's `t=day`), so the two no-cursor collectors now agree.

## `_TELEGRAM_MAX_AGE` — `deliver.py` GUARD 1, 12h → 24h

Sized as **"4 digest windows"** by the 2026-08-06 flood postmortem. At 6h, holding 12h would cut catch-up after failed runs from ~3 retries to ~1.

**This does not loosen the flood protection GUARD 1 exists for.** The bound that guard places on a backlog blast is measured in *windows admitted*, not hours — still 4, still far below the ~20 sends that tripped Telegram's 429 in the incident. GUARD 2 (the per-run 429 circuit breaker) remains the real backstop for the blast case.

Trade-off accepted deliberately: **a live-ping TL;DR can now be announced up to 24h stale rather than 12h.** If that reads as too stale in practice, this is the one line to revert — the RSS change stands on its own.

## Tests

The existing boundary tests passed at *either* value (1h fresh / 25h stale / 30h skipped are all unambiguous under both 12h and 24h), so **nothing in the suite would have caught a revert to 12h**.

Added one pin per constant at **18h** — inside the new window, outside the old one:

- `test_entry_between_the_old_and_new_lookback_bound_is_kept`
- `test_deliver_channels_telegram_freshness_window_sends_between_the_old_and_new_bound`

Verified both fail when the constants are reverted to 12h, and that no other test does.

The incident doc now records the change *and* the sizing rule, so the next cadence change re-derives from windows rather than copying the hours forward.
