## Description
## Why this exists

PR #11 made the X collector *work*; it did not make it *useful*. Your per-account post notifications arrive as one aggregate notification with `icon.id == 'bell_icon'`, `targetObjects: []` (no tweet at all) and `fromUsers` naming who posted — so the collector correctly skipped them and X contributed nothing. This PR makes notifications name the accounts and then fetches what they actually posted.

**Live-verified end to end:** 63 real posts collected from the notification-enabled accounts, summarized by Opus, rendered through the real email pipeline.

## Design

**Two phases.** Phase 1 (unchanged) builds mention/reply items from notifications that carry a linked tweet. Phase 2 resolves `fromUsers` → screen names via the page's own `globalObjects.users`, then calls `client.gql.user_tweets()` per account and parses raw JSON (same model-layer bypass as #11).

**Per-account post cursors — the load-bearing correctness rule.** Posts own `("x", "posts:{user_id}")` scopes rather than sharing the notification cursor. This is not incidental: a bell notification is timestamped *after* the posts it announces, so filtering posts against a cursor that notification advanced meant anything not captured in the same run — account posted more than one page, account beyond the per-run cap, fetch failed — fell permanently behind the cursor **while the run reported success**. With per-account cursors, a failed fetch leaves that cursor untouched (retried next run), capped-out accounts keep their position, and truncation advances but warns by name.

**No backfill on first sight.** A newly notification-enabled account seeds its cursor and emits nothing, mirroring first-run notifications and first-sight Telegram chats.

**Snowflake time decoding.** Post age comes from the tweet id (`(id >> 22) + X's epoch`) — exact integer comparison against the millisecond cursors, no date parsing, no timezone bugs.

**Retweet/quote containment.** `retweeted_status_result` / `quoted_status_result` subtrees are excluded from both extraction and author resolution: their nested originals carry their own `full_text`/`id_str`, and author resolution falls back to the notified handle (X's payload has no author data inside the post object), so traversing them would publish other people's posts under your followed account's name.

**Emission validation.** `screen_name` must match `^[A-Za-z0-9_]{1,15}$` and `tweet_id` must be digits-only; a malformed URL would no longer exact-match the emailer's anchor-provenance allowlist and would silently lose its deep link.

**Bounded and loud.** 20 accounts × 40 posts per run max, paced 1.5s apart, every cap and truncation logged by name — no silent caps. Phase 2 is wrapped like phase 1, so it can never propagate out of `collect()`.

## Review process

Codex is at its usage limit, so this went through an adversarial in-house review instead, which found the P1 above plus the retweet misattribution and the validation gap — all fixed here. It also caught that the *tests* were dishonest: the cap and failure tests asserted items and logs but never `cursor_updates`, making the loss class invisible. Four two-run permanence tests now cover exactly that. **Worth having Codex re-review this on main once your limit resets.**
