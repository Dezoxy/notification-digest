## Description
## Problem

The `positions` lane's quota is a **hard cap** — unlike every other lane, it never receives redistributed slots (deliberate: these channels were the crowding-out that `allocate_by_source` exists to prevent). That works fine as long as the lane's queue drains. It doesn't.

Measured on the VM, 2026-08-20:

| Channel | Arrives per 6h run | Backlog |
|---|---|---|
| `ASI_Alliance` | **60.5** | 309 |
| `fetchunofficial` | 16.6 | 88 |
| *(combined quota)* | *30* | |

`ASI_Alliance` alone is more than double the entire lane's cap. Combined inflow is ~77/run against 30 slots, so the queue grew ~188 items/day (397 waiting at time of measurement, lane live only since ~Aug 17–18).

Because selection within a lane is oldest-first, the 30 items reaching each digest come from the back of an ever-lengthening queue. Steady state is a backlog pinned at `prune_stale_unsummarized`'s 14-day horizon — a digest reporting **two-week-old chatter as today's positions**, while everything newer is deleted unread.

Surfaced while diagnosing an unrelated `digest.service` failure (`claude -p` timeout on the 00:08 UTC run); the allocation log line read `"positions": {"available": 397, "taken": 30}`.

## Fix

Select from the **tail** for lanes in the new `_NEWEST_FIRST_LANES` (only `positions`).

- Every other lane keeps oldest-first. Their quotas are floors that *do* receive redistribution, so their backlogs genuinely drain and the drain-loop contract (`_MAX_ITEMS_PER_DIGEST`) still holds for them.
- The starved tail ages out via the existing 14-day sweep — whose own comment already names this lane as the overflow it was written for. Accepted trade: high-volume community chatter loses its worth long before that sweep reaches it.
- Only the **choice** of items changes. The return value is still an oldest-first filter of the input, never a reorder, so `select_items_for_prompt` and `create_digest` are unaffected.

No config, schema, or prompt changes. Nothing outside `allocate_by_source`.

### The trap worth reviewing

`lane_items[-0:]` is the **whole list**, not the empty one. A newest-first lane allocated zero slots would silently be handed every item it had, breaking both its quota and the total budget. Hence the explicit `take == 0` guard, with a regression test.

## Tests

Three added, all against the real failure shapes:

- `..._positions_lane_takes_newest_not_oldest` — 400 positions items, budget 250: asserts exactly `telegram-370..399`, the inverse of the existing general-lane oldest-first assertion
- `..._positions_newest_first_preserves_input_order` — tail selection must not reorder the output
- `..._positions_lane_winning_zero_slots_takes_nothing` — the negative-slice regression guard
