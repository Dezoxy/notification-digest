# PR #71: fix(daily): guard run_daily against a duplicate timer fire

## Description
## The incident

On **2026-08-09** two daily briefs were produced 31 minutes apart — 20:06 (427 items) and 20:37 (386 items) Europe/Budapest. They were **not** one digest ingested twice: different item counts, different bodies, and the later one carried a whole section the earlier one missed.

They were two separate `python -m digest daily` invocations. `run_daily` had no "already ran today" gate — it synthesized whatever window digests fell in the sliding 24h `DAILY_LOOKBACK_WINDOW` and unconditionally called `create_digest(kind="daily")`.

A scan of the site's D1 archive confirms this is the **only** duplicate that has ever occurred. The stray row has been deleted from production (id 96 — the 20:06 one, which was the weaker brief); this PR fixes the cause.

## Why the app has to defend itself

The scheduling that decides *when* `python -m digest daily` runs is a systemd timer living **outside this repo** (CLAUDE.md's Deploy note). This code cannot assume that timer fires exactly once a day, so it has to be idempotent on its own — the same posture the SQLite state contract already takes for window digests.

## The guard

New **step 2** in `run_daily`: unless `--force`, skip the run as a harmless no-op when a `kind='daily'` digest already exists within `_DAILY_DUPLICATE_GUARD_WINDOW`.

| Decision | Rationale |
|---|---|
| **20h**, not `DAILY_LOOKBACK_WINDOW`'s 24h | Observed timer jitter is ~30 min, so a legitimate consecutive-day gap is ~23.5h — comfortably clear, while a same-evening double-fire is always caught |
| **Pure UTC recency**, never a Budapest-calendar-day check | CLAUDE.md: convert to Europe/Budapest only at render/email time, never in storage or state comparisons. No DST or local-midnight edge cases |
| **Reuses `get_daily_digests_since`** | Already returns `kind='daily'` rows at/after an ISO instant — exactly this shape. No new query |
| **After `deliver_pending`, before any `claude -p` call** | A stuck partially-delivered brief must still be retried on a skipped run, but no expensive work is done |

### Return value

Returns step 1's `all_ok`, **not** a hardcoded `True`. `main()` uses this only to pick the exit code, which is the sole Loki alert trigger — hardcoding `True` would mask a genuine pending-delivery failure, hardcoding `False` would spuriously alert on a correctly-skipped duplicate. This matches the sibling empty-day branch exactly.

`run_summary` gains `skipped_duplicate: true` so a Loki query can distinguish a skipped duplicate from an empty day (both otherwise log `source_digests: 0`).

## Backfill is unaffected

`scripts/backfill_daily.py` never calls `run_daily` — it inserts `kind='daily'` rows directly with a *historical* `created_at` and runs its own ±6h idempotency check. A backfilled past-evening row can never trip this guard.

One benign interaction, documented in the docstring: if backfill runs for *today's* boundary before the live timer fires, the live run correctly skips as a duplicate. That's desirable dedup, not a bug.

## Escape hatch

`python -m digest daily --force`. Matched to the existing bare positional-argv dispatch rather than introducing argparse for one flag.

## Tests

Five new tests, keyed off the constant rather than hardcoding 20h:

- duplicate within the window is skipped — no digest created, `summarize_daily`/`archive`/`publish_to_site` asserted never called, `run_summary` stamped
- a gap outside the window proceeds normally
- the first-ever run (no prior daily at all) proceeds normally
- `--force` bypasses the guard
- `deliver_pending` still retries a pending brief on a skipped run
