## The failure

```
2026-08-27 00:15:12 ERROR digest.deliver: site publish failed for digest 249: HTTPError
2026-08-27 00:15:12 INFO  digest.deliver: digest_delivery {"digest_id": 249, "site": "failed", ...}
```

Collectors and summarization were fine. The break is at delivery, and it is not one digest — it is every digest since the threshold below was crossed.

## Root cause

A cap mismatch on the ingest payload's `arc_contexts` array:

| side | constant | value |
|---|---|---|
| app | `_MAX_ARC_CONTEXTS_PER_PUBLISH` (`digest/state.py`) | **50** |
| site | `MAX_ARC_CONTEXTS` (`workers/news-site/src/config.js`) | **12** (`= MAX_TOPICS`) |

Past 12 entries `validateArcContexts` returns `badRequest` → **HTTP 400**, and that fails the *whole* PUT — an optional decoration takes the digest body down with it.

It also cannot self-clear: `_deliver_site` re-sends the same unscoped snapshot on every retry, so one crossed threshold stranded the site channel permanently rather than for a single run. Same poison-pill shape the `tldr or "(no summary)"` fallback in `publish.py` was written to avoid.

## Why the site's cap was wrong from day one

It was set by analogy with `MAX_DELTAS`: *"a digest can have at most MAX_TOPICS topics/arcs, so one ingest can never carry more primers than that."* True for `topics` and `deltas` — both per-digest. False for `arc_contexts`, and the same comment said so two sentences earlier (*"a per-arc primer, not a per-digest field"*).

`get_all_arc_contexts` is deliberately unscoped from `digest_id` — the full snapshot of every primer ever generated, which is exactly what makes primer publishing self-healing without a "has the site confirmed this" column. Nothing prunes `arc_context`, and `run_daily` adds up to `CONTEXT_MAX_PER_RUN` (3) rows a day. So the array's length tracks deployment age. Crossing 12 was a matter of time, not a possibility.

## Changes

- **`workers/news-site/src/config.js`** — `MAX_ARC_CONTEXTS = 50`, decoupled from `MAX_TOPICS`, with the false analogy written down so it does not get "tidied" back. 50 × `ARC_CONTEXT_MAX_BYTES` ≈ 400KB, ~20× under `MAX_REQUEST_BYTES`.
- **`digest/state.py`** — `_MAX_ARC_CONTEXTS_PER_PUBLISH` re-documented as a **hard parity constant** with the site's cap, matching `_MAX_TOPICS`/`_MAX_DELTAS`/`_MAX_ARC_KEYS`, instead of the "belt and suspenders" ceiling it claimed to be. Value unchanged.
- **`digest/deliver.py`** — log `HTTPError.code`. `400` (payload rejected, never self-clears), `401` (key), and `5xx` (site down) are three different problems that all logged identically as `HTTPError`, which is why this needed a code read to diagnose. Status code only — no `str(exc)`, no `exc.url`, no body read; unlike `publish.py`'s `_send_message`, this channel's key rides in a header, so the code carries no secret.

## Recovery

No app behavior change — the fix lands with the Worker deploy. Afterwards the backlog backfills itself: site publish is deliberately not age-windowed (`deliver.py`, *"the site is an archive and SHOULD backfill every pending digest regardless of age"*), and Telegram's own 24h `_TELEGRAM_MAX_AGE` guard keeps that backlog from flooding the topic. Each digest keeps its original timestamp and its own page; the index is week-bounded, so the site ends up looking as it would have if nothing had failed.
