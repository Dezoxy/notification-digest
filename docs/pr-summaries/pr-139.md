# PR #139: fix(relay): ping the hub topic so forwards actually notify the owner

## Description
## The problem

Owner-reported the day after the relay deployed: forwarded posts arrive **silently**.

Telegram never notifies an account about its own outgoing messages, and the relay forwards through the owner's own user session (`TG_SESSION`). So every other member of the hub gets a normal notification, and the one person the feature exists for gets none. Not a flag we set — the request carries no `silent` bit — a consequence of *who the sender is*.

## What I tested before building anything

Whether the **bot** could do the forwarding instead, which would fix it in one message. It cannot, measured against the live Bot API rather than assumed:

```
POST /bot<token>/forwardMessages
  from_chat_id=@Disaster_News  message_ids=[8882]  message_thread_id=555
→ {"ok": false, "error_code": 400, "description": "Bad Request: message to forward not found"}
```

The channel resolves; the bot just cannot see a message inside a channel it isn't a member of — the same limitation that forced the user session in the first place. Run on the VM so the token never left the box. One API call to close off the option.

## The fix

The forward stays on the user session, keeping the media, album grouping and "Forwarded from" header that a bot re-post would destroy. The already-configured notify bot then posts one line into the same topic:

```
🔔 Disaster_News · 2 new posts
```

Different sender, therefore a real notification, and the announced post is directly above it.

- **One ping per channel per run**, not per message — a batch of five is one event to a reader; five pings under five posts would be worse than the silence it replaces.
- **No link or button**, unlike every other sender in `publish.py`. `send_telegram_tldr` needs one because a window digest's home is the site; a relay post's home is the topic the ping is already in.
- **Soft-failing** (`_ping_relay_batch` never raises). The posts and their cursor are committed before it runs, so a 429 or revoked token costs one notification — not an `OnFailure` alert over content that already landed. Same posture `translate_digest` takes toward a failed translation.
- **No new config flag.** "The notify bot is configured" is already the only condition under which a ping is possible; a second switch would only be a way for the two to disagree.
