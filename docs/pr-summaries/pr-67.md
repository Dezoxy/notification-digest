## Description
App half of stable arc keys (site half: toom-edge #140, already deployed).

**The problem, from live data:** arc recurrence keyed on the heading fold, and headings are reworded every run — the Iran/Hormuz story appeared **11 times in 7 days under 11 different slugs**, never reaching the ≥2 threshold, so the NOW section showed one unrelated arc.

- **Prompt**: a ```arcs fence (immediately before ```deltas) carrying `{heading, key}` per story — same machine-facing pattern as §11.3, stripped at the same choke point so no channel renders it.
- **The feedback loop that makes it work**: a new `{{RECENT_ARCS}}` block replays the distinct keys used in the last 7 days, so the model *reuses* `hormuz` instead of re-inventing a key every three hours. Without it this would have re-fragmented with shorter strings.
- **Parser** `extract_arc_keys`: mirrors `extract_deltas` exactly — never raises, 12 cap, per-entry drops, two-fence = malformed, keys validated `^[a-z0-9][a-z0-9-]{0,47}$` on both extraction and replay.
- **Storage**: `arc_keys` table via `user_version` 2→3, idempotent `(digest_id, slug)` upsert; window runs only, with `run_daily`/`run_weekly` isolation asserted both structurally and behaviourally.
- **`derive_topics(body_md, arc_keys=None)`**: slug output verified byte-identical when no keys are passed — the §11.1 slug-stability contract is untouched, keys are purely additive.

**The finding that shaped the rollout**: `validateTopics` rejects *unknown per-entry* fields (a `...rest` check), so sending `key` to a pre-#140 site would 400 the entire publish — unlike top-level `deltas`, which older validators silently ignored. Hence site-first ordering, and `ARC_KEYS_SITE_ENABLED` survives as a kill switch (now defaulting **on**, since #140 is deployed; flip false to fall back to key-less topics without an app rollback — keys keep persisting locally either way, so no backfill on re-enable).
