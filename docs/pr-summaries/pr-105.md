# PR #105: feat(site): send arc_contexts as a delta, not a full snapshot
[View PR](https://github.com/Dezoxy/notification-digest/pull/105) · @Dezoxy · merged 2026-08-27 · `750ad8d` · `feat/arc-contexts-sync-delta -> main` · +365/-117 across 7 files

## Description
Closes the loop on #103/#104. Those fixed the outage and made its recurrence survivable; this removes the growth that caused it.

## Why not just prune

`arc_context` doubles as the **generation ledger** — `get_arc_keys_needing_context` qualifies an arc via `ak.key NOT IN (SELECT key FROM arc_context)`. Deleting a row silently re-authorizes a paid `claude -p` regeneration, which then overwrites a perfectly good primer on the site. Pruning trades **36KB of disk** for recurring model spend, against a feature whose core rule is "generate once, never regenerate."

The table was never the problem. The **send** is: every publish re-shipped the whole table, and the table only grows.

## Why now, and why not just let the cap clamp it

Measured on the VM — not extrapolated from the `CONTEXT_MAX_PER_RUN=3` ceiling, which never binds:

```
13 primers / 15 days = ~0.87/day, dead steady, ~2.8KB each
```

50 arrives in **early October**. (An earlier estimate of mine said "about a year" — that was wrong, and it's corrected in the PR-103 notes.)

Past 50 the existing `LIMIT` does turn the send into a newest-50 sliding window, which is *accidentally* almost correct — a primer gets ~57 days × ~5 publishes/day to land. But **its safety is a ratio nobody controls**: cap ÷ how fast the news cycle throws off new recurring arcs. Every future reader has to re-derive "is the window still wide enough?" from live data — the same class of dated, drifting invariant that caused the outage. The delta has no ratio to monitor.

## What this is

PLAN.md §11.6 rule 5 framed exactly this choice: *"send only unpublished primers, or the ones generated this run — pick one, make it idempotent either way."* The snapshot branch was taken only because the three-column table had nowhere to record what had been delivered. This adds the column and takes the other branch.

- **`state.py`** — `arc_context.synced_at` (nullable, `user_version` 5→6, ALTER pattern copied from the v5 `embed_url` step). `get_all_arc_contexts` → **`get_unsynced_arc_contexts`**, filtering `synced_at IS NULL`; renamed because a function called `get_all` returning a filtered subset is precisely the drift that causes the next bug. New `mark_arc_contexts_synced`.
- **`deliver.py`** — stamps exactly the keys a successful publish actually **carried**.
- **`publish.py`** — docstring only.
- **9 new tests**, PLAN.md updated in five places.

## The one subtle thing

#104's degraded path publishes with `arc_contexts=None` and **also succeeds**. Stamping on success alone would mark primers the site never received as delivered — stranding them permanently behind a manual escape hatch, a nastier version of the bug that path exists to survive.

So the rule is *what went on the wire*, not *did the call return*. Mutation-tested rather than asserted — swapping the degraded branch's `synced_keys = []` for the stamp-everything shortcut fails `test_deliver_site_degraded_publish_does_not_stamp_synced`, as it must.

## Migration: pre-existing rows stay unsynced, deliberately

Not backfilled to "synced", even though the site almost certainly has all 13. Backfilling assumes a delivery this database has no record of, and any primer that assumption got wrong would be stranded permanently. Leaving them NULL costs exactly **one** publish carrying the existing backlog, which the Worker upserts by key idempotently — as it has on every publish already. One redundant send beats one silently stranded primer.

## What this gives up

Self-healing by construction. If the site's D1 is ever rebuilt from empty, nothing here notices — there's no handshake, only this side's record of what it believes it sent.

That's already a manual-recovery scenario: a rebuilt D1 loses every digest row too, and `digests.site_published` stays 1, so nothing backfills those either. The escape hatch is one statement, documented in PLAN.md §4.19:

```sql
UPDATE arc_context SET synced_at = NULL;
```

An automatic periodic resync was considered and **rejected** as machinery guarding a failure mode D1 doesn't spontaneously have.
