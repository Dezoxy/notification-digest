# PR #101: fix(news-site): make the week-range label ICU-independent
[View PR](https://github.com/Dezoxy/notification-digest/pull/101) · @Dezoxy · merged 2026-08-26 · `741ecec` · `fix/icu-independent-week-range -> main` · +44/-1 across 2 files

## Description
The first git-connected build failed. The entire diff was one string:

```
- Week 35 · 24–30 Aug      ← golden, generated on macOS (ICU 77.1)
+ Week 35 · 24 – 30 Aug    ← Linux build image, newer ICU
```

Same code, same input, different bytes. `Intl.DateTimeFormat.formatRange` takes the range separator **and its spacing** from ICU locale data, and that isn't stable across ICU versions.

## The test failure is the smaller half

**Three** ICU builds render this label: the machine that generates goldens, the image that verifies them, and **workerd — what readers actually see**. The week rail's appearance on the live site was already being decided by whichever ICU the runtime shipped, silently, and nobody would have noticed until it changed.

Regenerating goldens on the "right" machine would have turned CI green while leaving that in place.

## The fix

Normalize the separator spacing. ICU still does all the locale work — field order, month abbreviation, collapsing the shared month — and only the drifting part is pinned. Tight is the documented intent; this label is specified as the `3–9 Aug` shape a few lines above in the same file.

Verified across every branch:

| | |
|---|---|
| en-GB | `24–30 Aug` |
| hu-HU | `aug. 24–30.` |
| year-spanning | `28 Dec 2026–3 Jan 2027` |

**All seven goldens pass unchanged** — that's the point. The fix makes the Linux build agree with the bytes already committed, rather than moving the goalposts to match CI.

## Documented

`test/README.md` gains the trap: if a golden fails only in CI and the diff is whitespace or a separator, suspect ICU before the code — and fix it in `src/` rather than loosening the comparison.
