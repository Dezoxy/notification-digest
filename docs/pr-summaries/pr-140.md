## Description
## The bug

`notify.js`'s newest-only rule *intends* that a backlog flush rings once, and both PLAN.md and the Worker README stated that as fact:

> "Only the newest rings … One ring, one brief, no repetition."

It never did. The check compares each digest against `MAX(id)` at **its own ingest moment**, so in a flush every digest is briefly the newest, claims, and rings.

**Measured live, not theorised.** Recovering from the site outage on 2026-09-04, digests 341 and 344 were republished 575 ms apart and both rang — showing identical content, because a payload-less push makes the service worker fetch `push/latest` and render whatever is newest by the time it opens:

```
#341  created 2026-09-03T18:40   pushed 2026-09-04T06:08:47.935Z
#344  created 2026-09-04T00:11   pushed 2026-09-04T06:08:48.510Z
```

## The fix

`PUSH_COALESCE_SECONDS` (60s): a digest claiming within a minute of the previous push claims normally but **skips the fan-out**.

- **Sized from the same incident.** The burst was under a second apart; that run's own genuinely-new digest landed 8.5 minutes later and must still ring. A minute sits far from both.
- **Placed after the claim, deliberately.** Skipping the fan-out *without* claiming would leave the row for the next retry to ring all over again — the exact repetition this removes.
- **Fails open** on an unparseable or backwards timestamp. A duplicate is dismissible; a silently dropped brief is not. That asymmetry picks the direction.
- **Lossless** — every digest in a flush would have rendered the same newest brief anyway.

## Tests

`notify.js` had **no direct coverage** before this. Four tests added, including a replay of the live 341/344 case. I verified they catch the bug rather than describe it: with the coalesce block removed, `a second digest seconds later claims but does NOT ring` fails; restored, all 48 pass.

The DB stub gains the `MAX(sent_at)` dispatch arm it would otherwise throw on — its "unrecognized statement throws" contract is what surfaced the need.
