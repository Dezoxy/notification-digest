# PR #136: feat: `relay` run mode — forward public-channel posts verbatim into a hub topic

## Description
## What

A fourth run mode outside the window → daily → weekly cascade. `python -m digest relay` forwards every new post from the public channels in `RELAY_TG_CHANNELS` into the hub group's `TELEGRAM_RELAY_THREAD_ID` topic, **verbatim** — Telegram's native forward, so media, albums, formatting and the "Forwarded from" header all survive. No summarization, no Claude call, no `items`/`digests` rows; the only state is one `cursors` row per channel under a new `relay` source.

Motivating case: a disaster-news channel (~1 post/day, mostly photos/video). The window collector extracts `msg.message` only, so a photo-only post is dropped outright — the wrong tool for this channel.

## Design (PLAN.md §4.22 has the full rationale)

| Decision | Why |
|---|---|
| **User session, not the notify bot** | The bot cannot read a channel it isn't a member of, so it has nothing to forward. Consequence: `TELEGRAM_NOTIFY_CHAT_ID` must be numeric when relay is configured — asserted in `Config.from_env`, bot token not required. |
| **Raw `ForwardMessagesRequest`, not `client.forward_messages`** | Verified against telethon 1.44: the wrapper exposes no `top_msg_id`/`reply_to` (can't target a forum topic) and doesn't chunk (one RPC per contiguous same-chat run, any size). |
| **Chunks ≤100 that never split an album** | `as_album` is a deprecated no-op; request boundaries are the only thing keeping a `grouped_id` run together. |
| **Cursor per chunk, deterministic `random_id`** | Cursor commits only after the RPC returns, so a crash replays at most one chunk — and `random_id = blake2b(chat_id:msg_id)` lets Telegram's own server-side dedupe drop the replay. (Window is time-bounded: next-hour retry yes, restore-from-old-backup no.) |
| **First run seeds, never backfills** | Same contract as `collectors/telegram.py`. |
| **Failure policy mirrors the collector** | FloodWait ≤60s → sleep + retry the chunk once; longer → abort the channel. `ChatForwardsRestrictedError` logged by username with a remove-it hint. One bad channel never costs the others. |
| **`_MAX_MESSAGES_PER_CHANNEL = 500`, a constant** | Runaway guard only, deliberately not an env var. |
