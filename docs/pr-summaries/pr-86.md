## Description
## Why

The quota system self-corrects for every lane that receives redistributed slots — a source that overflows one window is caught up by the next. What it can't do is **tell anyone when a lane stops draining altogether**.

That condition is invisible today: the run succeeds, exits 0, and delivers a perfectly healthy-looking digest, so `OnFailure=digest-notify.service` — the only alerting wired to this service — never fires. The positions lane accumulated for days exactly that way, and was noticed only because an unrelated `claude -p` timeout happened to put an `allocation` line under someone's eye.

This adds the missing smoke alarm.

## What

- `count_stale_unsummarized_by_source(conn, cutoff, positions_prefixes)` in `state.py`
- `_warn_on_stale_backlog` at the end of `_deliver`, logging a `stale_backlog` WARNING (JSON, Loki-queryable like `allocation` and `run_summary`)
- `STALE_BACKLOG_WARN_HOURS`, default **24h** = 4 window runs

**Age, not depth.** Queue depth is a proxy that a busy-but-healthy source trips constantly — `news` routinely carries ~120 waiting items and still turns them over inside one window. Age measures the thing that actually matters: an item nobody has written up yet.

**Report-only, deliberately.** Nothing retries, nothing reschedules, `all_ok` is untouched, and the query is wrapped so it can never take down a run that already delivered. A lagging source is a signal to go look at quotas or inflow — promoting it to a run failure would fire the owner's Telegram alert every 6 hours for something needing a considered fix, not a page.

## Threshold validated against the production DB

Ran the exact query read-only against `01-myapps-vm`:

| Threshold | Result |
|---|---|
| **24h (default)** | `[]` — **no warning** |
| 6h | flags `news` (47) — a healthy one-window deferral |
| 3h | flags all six sources |

The 24h result is the important one: it stays quiet *even with 354 items pending* from this morning's timeout, because that's normal remainder the next run drains. Anything at or below one window cries wolf. And 24h sits far below `_STALE_UNSUMMARIZED_PRUNE_DAYS` (14d), so it fires long before anything is discarded unread.

## The positions exclusion is load-bearing

That lane is hard-capped and, since #85, deliberately newest-first — a permanently starved tail is its *designed* steady state. Without excluding it, this warning fires on every run forever and trains the reader to ignore it. Confirmed against production: without the exclusion, 24h reports `('telegram', 200, '2026-08-18...')` right now.

## Corrected while building

I first wrote the exclusion with `COALESCE(lower(url), '')` to guard the SQL NULL-predicate trap (`NOT (x AND NULL)` is NULL, which drops the row). Checking the schema showed `url` is `TEXT NOT NULL`, `build_message_url` always returns a string, and production has **0 NULL / 0 empty across 15,056 rows**. The guard was defending an impossible state, so it's gone and the comment now records the real invariant — plus what would need to change if `url` ever became nullable.

The replacement test covers the edge case that *is* real: a private-chat `t.me/c/<id>/` item must still be counted, so the exclusion narrows to one lane rather than blinding the whole source.
