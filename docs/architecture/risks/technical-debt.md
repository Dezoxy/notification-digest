## Technical Debt

Debt that affects architecture, not code-level cleanups — those belong in the
repository's own backlog.

| ID | Debt | Why it exists | Cost of keeping it | Plan |
|---|---|---|---|---|
| TD-001 | The `arc_context` table (story-arc background primers) has no prune | It was added at schema version 3→4 for a deliberately durable feature — a primer is meant to persist, unlike an item or a digest row — and a prune was never designed alongside it | The table grows without bound as new arcs accumulate; no measurement of its current or projected size exists anywhere in this repository | None proposed in PLAN.md. Any future prune must not break `get_arc_keys_needing_context`, which treats an existing row as "already generated" — deleting one would silently re-authorize a paid regeneration |
| TD-002 | The "D1 is disposable and rebuildable from the VM" design intent has never been exercised end to end | [ADR 3](../decisions/0003-sqlite-is-the-source-of-truth.md) stated the intent from the start; building and actually running a rebuild procedure was not part of that work | If a real D1 loss happens, the rebuild path is exercised for the first time under pressure, with no prior evidence it produces a correct result ([A-03](../requirements/assumptions.md)) | None proposed in PLAN.md |
| TD-003 | End-to-end run latency (window close to delivery) has never been measured | The timer schedule is declared in the separate homelab repository, outside this repo's visibility, and no timing instrumentation was added when the schedule was set | Freshness ([QA-02](../requirements/quality-attributes.md)) is a stated quality attribute with no evidence behind it; a run that has become slow would currently go unnoticed | None proposed in PLAN.md |
| TD-004 | Hungarian delta text (`deltas_hu`) does not exist; the "What changed" block is suppressed entirely on Hungarian pages | `extract_deltas` strips the deltas fence before `translate_digest` ever sees it, so no Hungarian version of a delta is ever produced (PLAN.md §11.3) | Hungarian readers see digests without the "What changed" summaries English readers get, on every repeat-story window | Recorded in PLAN.md §11.3 as an explicit **OPEN GAP, unapproved** — the owner has not chosen between an extra translate call per window (cost) and folding delta text into the existing translate call (which routes machine-facing JSON through the translation prompt, a coupling the original design deliberately avoided) |
| TD-005 | `config.py`'s in-repo defaults for `VERIFY_DAILY_ENABLED` and `CONTEXT_ENABLED` (both off) don't match what actually runs in production (both on) | Each flag shipped default-off pending live validation against real output; validation succeeded and the flags were flipped on for the VM in the separate homelab repository's host variables, but the in-repo default was deliberately left unchanged (PLAN.md §11.4, §11.6) | Reading `config.py` alone misrepresents production behavior for two features that are, in fact, live and shipping every day | PLAN.md §11.4 records "flipping the in-repo default remains open and owner-gated" — no date, no committed step |
| TD-006 | A restore from backup can re-deliver a digest that was already delivered | `digests` rows carry per-channel delivery flags, and the pending-digest retry pass re-sends anything not flagged. Restoring a snapshot taken before a digest was flagged makes an already-sent digest look pending again. Backups and the retry pass were each designed correctly in isolation; nothing reconciles them | Directly contradicts [QA-01](../requirements/quality-attributes.md), the one absolute guarantee this system makes. Latent: it costs nothing until the first real restore, which is also when it is hardest to notice | None. Today the mitigation is manual — after a restore, check which digests were pending as of the snapshot before the next timer fires. See [backup-strategy.md](../reliability/backup-strategy.md) |

### Review

Reviewed together with [architecture-risks.md](architecture-risks.md) whenever
PLAN.md's own roadmap is revisited. Debt tracked here is either scheduled in
PLAN.md, explicitly accepted, or removed from this list — nothing appears here
